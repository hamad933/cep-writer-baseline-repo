## Learning outcome
Given an authorized scenario, distinguish the trust boundaries, apply the mechanism and controls for API Object-Level Authorization, identify observable failure evidence, and state what remains unproven.

## Scope and boundaries
Per-object authorization using server-resolved identity and policy, independent of attacker-supplied identifiers.

## Prerequisites
CC-D01-001 foundations; CAP-D05-0009

## Internals and mechanisms
Authorization telemetry should preserve when, where, who, what action, what resource class and safe identifier, tenant, decision, reason or rule, policy version, request correlation, and response status, while avoiding raw access tokens, session identifiers, secrets, and unnecessary sensitive object data. API authorization is an explicit decision over an authenticated actor, requested resource or object, requested action or function, and relevant context such as tenant, relationship, attributes, and policy state. Authentication alone and possession of an identifier do not establish permission.

## Attacks and failure modes
Horizontal authorization abuse commonly replays an otherwise valid request while substituting another user or tenant object identifier, including identifiers in paths, query parameters, bodies, batch lists, or nested API inputs.

## Detection and observation
Use as the authoritative join point for actor-resource-action decisions; require an event for sensitive allows and denials, and flag privileged actions with no corresponding decision event. Validation: Run one allowed object action, one foreign-object denial, and one privileged-function denial; confirm complete, correlated events without raw tokens or secrets.

## Prevention, remediation, and controls
Unpredictable identifiers, including GUID-like values, reduce casual enumeration but are defense-in-depth and do not replace object authorization on every access.
