### 1.0.1 Controller succession / chat-boundary continuity law — OD-20260922-077
































A Controller chat boundary is a continuity event, not a reset, acceptance event, new mission, or new architecture epoch. The successor becomes the direct and sole final accountable Controller to the Owner only after independently reconstructing current truth through the mandatory boot and exact current source/mission/evidence.
































The predecessor Controller MUST, before handoff when tools permit:
- refresh live authority/current state and pending result/output custody;
- update the same `CURRENT_STATE.md` when continuity/next-action truth materially changes;
- record any new durable Owner decision in the live decision register;
- update existing durable lessons/gaps/method files in place when a transferable lesson materially improves future control;
- update the stable `CONTROLLER_SUCCESSION_HANDOFF.md` in place instead of creating parallel dated succession state files;
- bind exact current source/candidate identities, open blockers, accepted/salvageable classifications, pending Writer/Auditor state, next legal action and hard prohibitions.
































The succession handoff and bootstrap prompt are `SUPPORTING_CONTINUITY__NOT_AUTHORITY`. They may be comprehensive, but they never override `READ_FIRST`, `CURRENT_STATE`, governance, live Owner decisions, exact accepted/candidate evidence, mission/profile/oracle truth or a newer Owner instruction.
































First-turn successor procedure:
1. perform the mandatory boot independently;
2. compare live state against the handoff and treat live authority as controlling on any divergence;
3. recheck pending Writer/Auditor/output folders because results may have arrived after handoff preparation;
4. if a result exists, audit it rather than relaunching; if none exists, continue the already-authorized exact work item without rebuilding solely because the chat changed;
5. preserve all accepted/candidate lineage, owner locks, truth ceilings and Stop Gates;
6. update `CURRENT_STATE.md` only for a material state change and re-read it before replying.
































Never ask the Owner to reconstruct governed history that Drive/GitHub evidence can resolve. Never use predecessor confidence, a prompt, chat memory or a handoff summary as acceptance/source truth.

Authority precedence resolves which current source controls, but it does not collapse distinct truth dimensions into one another. Every implementation and review must resolve these dimensions separately:
































































































































































































































































- **Owner intent and corrections:** latest explicit Owner decision and applicable live decision rows.

- **Shared Presentation and mechanics:** global/family owners for layout grammar, slots, pane/window behavior, focus, menus, editor mechanics, responsive behavior and interaction patterns.
- **Visual reference:** the classified reference image for applicable Presentation value and state.
- **Implementation and evidence:** exact source/candidate identity plus source-bound runtime/browser/visual proof.

In particular:
































































































































































































































































- a shared Presentation owner may determine **how and where** a compatible action or region is presented, but never invent, remove or rename the Surface's domain commands, workflows, lifecycle, data or provider semantics;
- a Surface profile may determine **what** the Surface means and does, but may not fork a compatible shared pane, editor, toolbar, focus, window or interaction mechanic;
- a visual reference may require Presentation hierarchy and value, but may not fabricate domain/provider truth or supersede newer Owner corrections;
- Library is a donor and consumer for compatible reusable value, never the universal semantic or action-inventory template for all Surfaces;
- Learn may inherit the maximum compatible Structured/Library mechanics while retaining Learning-specific commands, workflow and data truth; other Surfaces inherit only the shared mechanics applicable to their own identity.

1. `WRITER_LOCAL_VISUAL_CAPTURE_AND_RENDERING_METHOD.md` (or exact accepted successor) as the operational capture/recovery/evidence-class method.
2. `FINAL_VISUAL_REFERENCE_REGISTER.md` / `ORACLE-009` for exact visual-reference IDs, hashes and authority ceilings.
3. `23_SURFACE_ZERO_LOSS_IDENTITY_REFERENCE_MATRIX.md` / `ORACLE-013`, the exact affected SurfaceProfile(s), `CEP_FINAL_VISUAL_INTERACTION_CONTRACT.md` / `ORACLE-010`, and applicable domain oracle(s) for Surface purpose, workflow, lifecycle, data/provider truth and region/command ownership.
4. Exact reference-image binaries or a deterministic local projection of them. A filename, Drive link or screenshot remembered from chat is not sufficient authority.
5. Source-bound evidence identity: candidate HEAD/tree/Product identity, build identity, browser/automation executable/version, viewport, state, direction/theme, render mode and capture hash/path where custody requires it.
6. Data-sufficiency classification for every reference-backed state: `REAL_CURRENT_DATA`, `GOVERNED_ACCEPTANCE_SEED`, `TEST_ONLY_PRESENTATION_HARNESS`, or `TRUTHFUL_EMPTY_UNAVAILABLE`. An empty screenshot cannot prove parity with a populated reference. When lawful populated Product truth is unavailable, capture truthful normal Product state plus a separately labeled matched Presentation diagnostic state through an admitted test/acceptance seam, or return `VISUAL_PARITY_NOT_ADJUDICABLE__DATA_COVERAGE_BLOCKED`.
7. State/viewport matching. Direct parity is adjudicable only when reference and candidate are materially aligned in viewport, relevant Product state, selected object/context and data/source class. Mismatched images may support diagnosis but not parity PASS.
8. The governed comparison sequence: `GOVERNED REFERENCE -> CURRENT NORMAL CAPTURE -> MATCHED DATA/STATE CAPTURE -> FULL-FRAME COMPARISON -> COMPONENT/REGION/STATE CROPS -> DOM/NETWORK/CONSOLE/ACCESSIBILITY/INTERACTION INSPECTION -> FINDING -> ROOT CAUSE`. 9. Region/crop decomposition. Compare material TOP/TOOLBAR/LEFT/CENTER/RIGHT/BOTTOM/TRANSIENT regions and material components independently; use matched crops/locator captures or bounded image crops when they materially increase precision. Preserve reference identity and never reinterpret a crop as an independent authority artifact.
10. Material component/state census. For each applicable component verify default/hover/focus/focus-visible/active/selected/disabled/unavailable/expanded/collapsed/loading/empty/stale/error/conflict/read-only/processing/success plus typography/hierarchy/spacing/density/icons/borders/contrast/overflow/z-index/first viewport/responsive geometry/RTL/LTR/Bidi/technical-token isolation/pointer/keyboard/focus entry-return-fallback/dismissal/Back-Forward/accessibility/reduced motion where applicable. `NOT_APPLICABLE` requires a reason; screenshot quantity is completeness-driven, not quota-driven.
11. Actual visual inspection. PNG/WebM existence, browser PASS, DOM assertions or green tests never substitute for opening/inspecting the material image/frame/state. Screenshot != parity; green test != Presentation PASS.
12. Full-carrier negative falsification. Verify both that required Surface semantics/regions/actions are present and that donor/debug/foreign-Surface semantics not authorized for that consumer are absent.
13. Four truths remain separate: CONTENT; PRESENTATION; BEHAVIOR/INTERACTION/FUNCTIONALITY; DOMAIN/DATA/PROVIDER TRUTH. Visual references are Presentation authority only and never fabricate provider/domain truth.
14. Capture capability separation and recovery ladder from `OD-20260922-072`: browser launch, URL navigation, navigation-independent rendering, JS/DOM, pointer/keyboard interaction, screenshot creation, actual image inspection, video and genuine route/platform proof are separate capabilities. Navigation failure alone does not justify stopping truthful Presentation capture.
15. Evidence custody follows `OD-20260922-073`: intermediate captures/crops/diffs/logs are local execution scratch by default; promote only final representative source-bound evidence required for handoff/audit. Do not use GitHub as bulk visual-evidence transport.

For reviewer missions that combine capture and adjudication, use two explicit phases without collapsing them:
- `PHASE A — SOURCE-BOUND VISUAL EVIDENCE CENSUS`: generate the complete current-state capture set and prove its identity/data/state/viewport coverage before judging parity.
- `PHASE B — REFERENCE / AUTHORITY DEEP AUDIT`: compare the Phase-A evidence to current references, profiles, interaction contract, surface matrix and applicable domain oracles using full-frame + region/component/state crops and direct behavior/data corroboration.

A missing visual-method/reference/profile/oracle binding in a Controller-issued visual mission is a mission-design defect; do not silently replace it with worker memory, generic aesthetic judgment or broad repository archaeology.
