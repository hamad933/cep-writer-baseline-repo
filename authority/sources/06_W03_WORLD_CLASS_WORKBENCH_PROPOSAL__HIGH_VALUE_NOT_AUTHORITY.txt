====================================================================
0. CORE PRODUCT THESIS
====================================================================

W03 MUST FEEL LIKE A COMPLETE PROFESSIONAL CYBER-SIMULATION WORKSTATION.

Do NOT design W03 as:

- a graph editor;
- a collection of cards;
- five disconnected pages;
- a topology viewer;
- a dashboard;
- a fake terminal shell;
- a node-and-edge drawing application;
- a visual-only prototype;
- static devices connected by decorative lines.

The experience should feel conceptually closer to the strongest qualities of:

GNS3
Cisco Packet Tracer
Cisco Modeling Labs
EVE-NG
professional IDEs/workbenches such as VS Code
professional terminal managers
packet-analysis and cyber-operation workstations

but W03 should NOT blindly clone any one product.

The North Star is:

"I can build a complete simulated environment, bring it alive, interact with
its devices and services as if they were meaningful operational systems,
operate multiple terminals/tools simultaneously, observe causality and
telemetry, troubleshoot the environment, execute training scenarios/labs,
and later replay and analyze exactly what happened — while remaining inside
one coherent customizable professional workspace."

====================================================================
1. THE MOST IMPORTANT PRODUCT PRINCIPLE
====================================================================

W03 is ONE CONTINUOUS WORKBENCH.

The five conceptual surfaces are:

ENTERPRISE
SCENARIOS
LABS
RUNS
RESULTS

but do NOT make them psychologically feel like five unrelated applications.

They should participate in a continuous workflow:

BUILD / MODEL
→ PREPARE
→ RUN / OPERATE
→ OBSERVE
→ REPLAY / ANALYZE

Preserve as much spatial, object, selection and operational context as possible
while moving between these stages.

Example:

The user builds a network/environment.
They select "Run".
The environment does NOT disappear and get replaced with an unrelated dashboard.

Instead:

- the same or equivalent topology becomes the Runtime projection;
- device states become alive;
- links show runtime state;
- operational tools become available;
- commands produce state changes;
- telemetry/events appear;
- tasks/scenario progression activates;
- the user remains oriented inside the same environment.

When the Run ends:

- Results / Replay should retain device identity;
- topology context should remain recognizable;
- selecting an historical event may highlight the exact device/link/service;
- historical tools become read-only historical views where appropriate.

====================================================================
2. BUILD MODE != RUN MODE, BUT THEY SHOULD FEEL CONTINUOUS
====================================================================

Separate authored truth from runtime truth.

BUILD MODE:
- edit definitions;
- add/remove devices;
- connect interfaces;
- configure intended properties;
- design Digital Twin;
- define Scenario;
- define Lab;
- configure initial state.

RUN MODE:
- operate a frozen runtime projection;
- interact with devices;
- issue simulated commands;
- observe runtime state;
- generate events;
- inspect telemetry;
- execute tasks;
- pause/resume/stop;
- troubleshoot.

Never silently let a Run mutate the authored source definition.

Possible future professional command:

PROMOTE_RUNTIME_CHANGE_TO_NEW_DRAFT

but this should be explicit.

The UI should make the mode clear without making the user feel they entered
a completely different application.

====================================================================
6. TWO DIFFERENT KINDS OF PINNING
====================================================================

Evaluate and preferably support both concepts:

PIN_TO_VIEWPORT

The terminal/window stays in the same screen position while the canvas
pans/zooms behind it.

ANCHOR_TO_DEVICE

The terminal/window remains associated spatially with the device/node.

Example:

A tiny terminal can appear near Router-01.

If the topology moves/pans, the shell follows Router-01.

The user may convert:

ANCHOR_TO_DEVICE
→ PIN_TO_VIEWPORT
→ DOCKED
→ CENTER_TAB

without destroying the session.

46. RESPONSIVE DESIGN
====================================================================

Primary professional target:

large desktop.

Also design intentionally for:

1440+
standard desktop
~1024
compact/narrow fallback.

Do NOT simply shrink everything.

At medium widths:

- side panes may become overlay;
- splits may collapse to tabs;
- floating sessions may snap into manageable layouts;
- Session Shelf may become compact;
- inspector may become drawer.

At very narrow widths:

the goal may be VIEW/OPERATE fallback rather than full topology authoring.

Preserve recoverability:
the user must always be able to reopen hidden regions.

====================================================================
47. PERFORMANCE / SCALE
====================================================================

Design for large environments.

Avoid mounting hundreds of heavy terminal/UI instances simply because
hundreds of devices exist.

Consider:

lazy session creation
suspended background sessions
canvas virtualization
progressive rendering
telemetry batching
event streaming
terminal buffer limits
large topology LOD
selective animation
visibility-aware updates

Maintain state integrity.

====================================================================
67. FINAL NORTH STAR
====================================================================

The completed W03 design should make the following experience possible:

The user opens W03.

They see a professional, customizable cyber-simulation workstation.

They build an environment with real semantic devices and relationships.

They create or select a Scenario/Lab.

They start a Run.

The same environment comes alive.

Devices boot/change state.

Links become operational.

They double-click a router.

A realistic terminal opens.

They drag the terminal beside the router.

They anchor it to the device.

They open another terminal and split the workspace.

They open an Event Viewer for another system.

They issue commands.

The simulation state changes.

Other devices react.

Events and telemetry appear.

Tasks progress because of actual simulated state, not button clicks.

They pause the Run and inspect the environment.

They resume.

They finish.

Results opens without destroying their mental context.

They scrub the timeline.

The affected devices highlight.

They inspect historical terminal output.

They write AAR notes without modifying history.

They compare another Run.

Throughout all of this:

- the workspace remains theirs;
- panes can be moved;
- terminals can float/dock/tab/split;
- layouts can be saved;
- keyboard-only operation is possible;
- screen reader users have a semantic non-spatial route;
- Arabic chrome and technical English remain readable;
- the experience feels like one coherent professional application.

THAT is W03.
